The REACT COMPOSITION API — the top architectural layer, AND the home of the fleet-wide composable-component convention. Compose an entire park as JSX on ONE shared canvas instead of hand-writing an imperative `build`: `<Park>` renders a single Stage (full-screen by default, autoRotate OFF, fog, terrain-clamped camera), the `<GameManager/>` child declares the ONE `createGameManager`, clickability comes wired (ride click → RideViewer with onboard cam, guest click → GuestInfo — one floating window at a time), ParkInfo mounts bottom-right and `validatePark` runs one frame after the children settle. Every child is a thin declarative wrapper over the existing imperative builders — the recipes in `rules/park-generation.md` still apply unchanged; the wrappers just execute them. This is a HAND-ROLLED context, NOT react-three-fiber.

**The composing agent's flow:** seed a `<Terrain>` → lay `<Paths>` → declare `<GameManager/>` → mount the `<Gate>` (park entrance) → creatively place attractions straight from the catalog (`<FerrisWheel position rotation register/>`, `<BurgerShop register/>`, `<Torch/>`, …) → scenery. Once the `<GameManager/>` exists, ALL game logic is free: guest spawning/needs/goals, ride FSMs + breakdowns, queues, purchases, litter, and the UI windows.

**Composition order is mount order.** Sibling effects run in JSX order, so declare `<Terrain>` → `<Paths>` → `<GameManager>` → `<Gate>` → rides/stalls/amenities → scenery, exactly like the imperative build order. Wrappers throw a descriptive error when a prerequisite is missing.

```tsx
<Park seed={7} climate="temperate" size={16} guests={10} onReady={(report) => {/* ok? */}}>  {/* compact demo — omit `size` for the EXPANSIVE 128 default and SPREAD OUT (3-5 districts, 8+ rides, first queue tail within 15 u of the gate) */}
  <Terrain keepDry={KEEP_DRY} coasterPts={COASTER_PTS} />
  <Paths nodes={NODES} edges={EDGES} plazas={[PLAZA]} walkers={4} bins={[[1.5, 2.4]]} />
  <GameManager />
  <Gate />
  <Coaster name="Timberline Run" points={COASTER_PTS} type="wooden" capacity={3}
    queueTailNode={12} queueDir={[0, -1]} deck={[-4.31, 0]} />  {/* `exit`/`exitDir` OMITTED — the chassis derives the RCT2 pair */}
  <FerrisWheel position={[6.69, -2.4]} rotation={-Math.PI / 2} register={{ name: 'Grand Wheel', capacity: 4 }} />
  <BurgerShop position={[3.0, -0.5]} rotation={-Math.PI / 2} register price={3} value={5} />
  <Fountain /> <Restroom position={[-1.2, 4.8]} rotation={Math.PI / 2} />
  <Torch position={[1.65, 4.05]} /> <Neon text="ARCADE" position={[3.6, 1.7, -6]} rotation={Math.PI} />
  <Scenery name="planterBox" position={[1.65, 0.75]} /> <Lights from={[-0.95, -1.2]} to={[0.95, -1.2]} />
  <Placed build={(t) => tree(t, { shape: 'pine' })} position={[-2.8, 4.6]} />
</Park>
```

## The composable convention (fleet-wide)

Every catalog component exports ONE React component that COMPOSES: it mounts its built group into the surrounding scene context and renders null. **No component renders a `<Stage>`** — the only Stage owners are `<Park>` and `<ScenePreview>` (the host `*.previews.tsx` files use). All of it is exported from here:

- **`useComposable(build, { position, rotation, scale, deps }) → boolean`** — the primitive: `build(t, park) → Group | { group, update?, dispose? }` runs in an effect, mounts via `addObject` with the prop transform (y settles via `floorAt` unless `[x, y, z]`), cleans up on unmount, REMOUNTS on prop change (`deps` = extra remount key; builder identity is NOT a key). Returns false outside any scene context.
- **`composable(displayName, build, cfg?)`** — the factory: `build(t, props, park)`; `cfg.props` defaults; `cfg.compose(park, { built, props, position, rotation, scale }) → cleanup?` is the registration hook, run ONLY in real parks (never under a preview host).
- **`<ScenePreview distance targetY autoRotate ground background night height fog groundAt seed dress>`** — the preview Stage host: provides the same context (usePark works; `groundAt`/`floorAt` → 0), `dress(t, g, api)` builds staging around the children and may return an updater. Keep previews pixel-identical: same Stage props as the old per-component Stage.
- **`<ConfigurableRide build layout register name capacity rideDuration loadTime intensity price queue position rotation scale>`** — the universal ride chassis (every catalog ride renders one via `composableRide(displayName, build, layout)`). With `register` (or any top-level sim prop) inside a real `<Park>` it does EVERYTHING: `registerRide` (FSM: waiting → departing → travelling → brokenDown/beingRepaired; the builder's `onStateChange` spins the visual down/up), queue lane + entrance/exit huts derived from position+rotation via `layout` (`front` — queue HEAD out the local +z face, default 1.8; `exit` — a SIDE HINT ONLY, not a coordinate: only the SIGN of its local x is read (default `[-1.5, 1.35]`), the chassis places the hut one tile along the station face itself; `board` local `[0, 0.25, 0]`; `defaults` — per-ride name/capacity/duration/intensity/price), `groundRideAccess` grounding, `seatWorld` pass-through (real guests ride the vehicle), `crashed` crash wiring, `userData.rideRef` (click → RideViewer) + `userData.rideVehicle` (onboard cam). `queue={{ anchor, dir }}` overrides the derived lane in world space. LANE LENGTH (round-2 safeguard): the derived lane always rotates with the ride (its axis is the yaw-rotated local +z); by default it is `laneLenOf(capacity)` long, but when a STREET NODE sits on the lane axis short of the default tail reach (`front + laneLenOf(capacity) + 0.35`) the lane is TRIMMED so its tail lands exactly on that node — layouts planned against the documented `1.8 + 0.35·capacity + 0.35` footprint used to have their lanes overshoot the street and spear into a facing ride's lane. Never extended; ≥ 1.2 u of lane is kept; explicit `queue` overrides opt out. Place rides so a street node sits on the +z lane axis within that reach. `registerComposedRide(park, built, reg, at, layout, queue?)` is the underlying helper.
- **`<ConfigurableStall build stall register name price value>`** / **`composableStall(displayName, build, saleDefaults)`** — the shop chassis: `registerStall` with the anchor at the settled position and the serving front facing local +z (attach point 0.72 out — aim `rotation` at the customers' path). Guests then hunger/thirst-seek it, buy, and litter.
- **`<GameManager guests?>`** — declares the sim explicitly (mount right after `<Paths>`); `guests` overrides `<Park guests>` (the OPENING population — more keep arriving through the gate, see `<Park>` below). Legacy parks that never mount it still get a lazily-created manager (with a console note), but the JSX child is THE way.

**Exemplars:** `FerrisWheel` (ride: seatWorld gondola riders, FSM spin-down, vehicle cam, layout geometry in its doc comment), `BurgerShop` (stall + `withGuest`), `Torch` (simple + rich preview dress), `GrassTile` (minimal). The demo park composes all of them, `validatePark ok: true`.

**Migration checklist** (any new/remaining component): 1) extract the builder `build<Name>[Scene](t, opts?) → { group, update? }` (+ `seatWorld`/`vehicle`/`onStateChange`/`crashed` on rides); 2) componentize with `composable`/`composableRide`/`composableStall` — keep every existing export; 3) previews render the component inside `<ScenePreview>` with the SAME Stage props (staging → `dress`); 4) cleanup audit (dead code, unused imports) + esbuild + day/night screenshots standalone AND composed (rules/asset-testing.md still gates).

**Track piece composition (future work):** tracked rides will take pieces as props/children compiled to spline control points (TrackKit-style). Not built yet — do not hand-roll per-ride piece APIs.

Exports:

- **`<Park seed climate size fullscreen height validate guests background fog distance cameraPose quality budgets onReady>`** — the one canvas + sim + UI shell. `fullscreen` defaults **true** (rules/ui.md); `validate` defaults **true**: one frame after the children mount it spawns `guests` at the gate — the OPENING POPULATION, default `guestsForSize(size)`: **~50 on the 128 default plot** (13 at 16, 26 at 48, 66 at 192; the crowd grows with the cube root of plot area, fitted to the corpus counts that were rendered and scored good — see `parkContext.ts guestsForSize`). They keep coming: with a `<Gate>` registered, guests continue to ARRIVE through the archway on RCT2's own guest-generation curve, gated on aggregate happiness, up to the hard ceiling `guestCapForSize(size)` = 2× the opening count clamped to [24, 160] — 26 / 52 / 100 / 132 at size 16 / 48 / 128 / 192 (GameManager/Context.md "The gate stream"). Pass an explicit `guests` for a park that must open on an exact roster, runs `validatePark` (net/manager/terrain/registered coasters/extra footprints/scene group, plus `gridNodeCount` so diagonal street edges FAIL), logs the report, shifts the render clock past the sim smoke run (by the report's `simSeconds` — the window scales with the longest registered rideDuration) and calls `onReady(report, { manager, api })`. `size` defaults to **128** since 2026-07 (wave 8 had made it 192 and it was a THIRD too big — the land read as an empty green field; sizes from 16 to 256 compose + validate, and everything downstream — terrain seg density, composition zone counts, water-body count, validators, orbit distance — scales with it). Plots ≥ 64 compose TWO water bodies (a dominant one + a secondary); ≤ 48 keeps the classic single body. `fog` defaults to the classic haze, or `{ near, far }` culling fog when `size > 20` (so the default 128 gets culling fog; `fogRangeFor` has a distinct big-plot branch past size 48 that scales the haze wall off the orbit radius — at 128 it sits at **109-237 u** — pair with the ride runtime's LOD tiers). `quality` (default `'medium'`) picks the Stage rendering tier; `budgets.lights` caps simultaneously ACTIVE PointLights park-wide and is **OPT-IN — there is no default cap** (it used to default to 16; see "Lights are no longer throttled" below). Prop changes on `<Park>` itself need a remount (`key`).
- **The ride runtime (automatic):** every mounted object is LOD-scheduled — NEAR full detail every frame; MID every 2nd frame, `userData.lodDetail` children (passengers, cockpit dressing) hidden; FAR every 4th frame, particles + its PointLights shed (static silhouette); OFFSCREEN paused to a 32nd-frame keep-warm tick. Distances are measured against ALL cameras (orbit + insets), boundaries have hysteresis, and updaters take absolute time so throttling never slows or drifts motion. A `[Park] perf:` line logs ~3 s after settle. See SETUP.md §13.
- **`usePark(consumerName?)`** → `ParkContextValue` for custom children: `{ three, root, api, seed, size, climate, addObject(obj, updater?, { lod }?) => cleanup, manager(), ground, paths, composition, groundAt(x,z), floorAt(x,z) (plaza-aware), registerFootprint(rect), registerCoaster(c), reportLint(kind, detail, fatal?), registerPlanted(p), registerBlocker(spec) }`. `registerBlocker({ rect | circle, label, kind?, owner?, pad?, height? })` declares a SOLID obstacle guests must walk around (round-6 — see below); it forwards to the GameManager's blocker registry and returns the unregister (a no-op before `<Terrain>`/`<Paths>` exist and under `<ScenePreview>`). `addObject` registers a ride-runtime entry — pass `{ lod: 'full' }` for park-spanning backdrops that must never throttle. `manager()` creates the ONE GameManager lazily (requires `<Terrain>` + `<Paths>` mounted; its group joins the scene automatically).
- **`<Terrain seed? climate? size? keepDry coasterPts noDress? seg?>`** — `parkComposition` (probed landform under YOUR guards) + `buildTerrain` + `tintTerrainForClimate` + ONE `buildWater` sheet; registers `heightAt` as the Stage ground sampler. Always the first child. **Guards are POST-ENFORCED (round-3 safeguard):** the composition's `clampPeaks`/`clampBasins` are built into the real terrain, so every `keepDry` cell and coaster footing comes out dry and bulge-free even when no probe seed satisfied the rules — `comp.report.violations` (what validatePark receives) reflects the post-clamp ground.
- **`noDress` — GROUND THAT MUST STAY BARE, without moving the ground.** Regions the climate auto-dressing may not plant in: discs `{ x, z, r }` and/or `ParkFootRect`-shaped rects `{ cx, cz, hx, hz, yaw? }` in world coords (so `plan.footprint`, `plan.extent` or a ride's `trackBox` drop straight in). **Do not reach for `keepDry` to stop planting:** keepDry promises dry, walkable, flat-ish ground, so it fires the guard clamp and MOVES the heightfield, which moves the walk network the acceptance sim has to cross — that is how the Emberfall Caldera land's "cacti on fresh lava" fix once turned into a FATAL `sim: no guest completed a ride cycle in 70 sim-s` (that land macro was removed in v6.0; the lesson stands). `noDress` suppresses planting/scatter ONLY: mesh, `heightAt`, clamp, zone paint and water are identical with or without it, and an omitted/empty list dresses bit-identically to before the prop existed. A land that paints its own floor publishes its regions — `<Terrain keepDry={NET.keepDry} noDress={LAND.noDress} />`.
- **`<Paths nodes edges plazas grid nodeY width walkers bins>`** — the lattice street skeleton: `snapNetToGrid` safety pass, ONE path level (max ground under nodes + 0.03), `buildPathNetwork` (grid lint default ON), `bermNetToGround`, ambient `attachWalkers`, bin meshes + manager bin registration. CAUSEWAY LINT (re-armed round-6, now §0-FATAL): two tests — the path level sitting > 0.8 u above the MEDIAN ground under the nodes (one node on a rise lifts the whole network onto tall berms) AND **every rendered SPAN sampled against the ground beneath it** — a street whose nodes all sit high but whose span crosses a river bank is quietly put on a wooden viaduct, and a round-6 park hoisted an edge 2.21 u with the old node-only lint silent. A span lifted > 1.0 u is recorded as a FATAL park lint (`validatePark` fails it, check `autofix`) — reroute the edge, add an intermediate node on buildable ground, or `nodeY`-ramp down to it. Diagonal street edges are promoted from a lint warn to a validatePark FAIL.
- **`<Gate position? rotation?>`** — `buildParkEntrance`, plinthed, `registerParkEntrance` = the SOLE guest spawn. DEFAULT position snaps to the lattice cell hugging the FRONT (+z) terrain edge (z = `1.2·round((size/2 − 0.8)/1.2)`: **63.6 on the default 128**, 22.8 on a 48, 7.2 on a compact 16 — within ~1 u of the edge, facing OUT; round-3 safeguard: the old default sat 2 u inside and failed validatePark's gate-at-edge check). Keep a street node under the gate cell.
- **`<Coaster points type bank name capacity rideDuration loadTime intensity price cars colours queueTailNode queueDir exit? exitDir? deck>`** — `points` are `[x, yAboveRef, z]` (the 80th-percentile ground-reference trick is applied for you; points 0-2 = the station straight, levelled flat). Builds `buildRideSpline` + a ColorKit-preset train + station deck, plans the queue/hut assembly with `planRideAccess`/`groundRideAccess` (queue TAIL on street node `queueTailNode`), registers with the manager (`vehicleHandle` crash wiring included), tags `userData.rideRef`/`rideVehicle`, and registers the circuit for validatePark's legality + crash checks. Pieces mode forwards the park size as `compileTrackPieces` `bounds`; a FATAL compiled circuit (checks failed / closure > 40% of the authored length / out of bounds) is rendered as a TRANSLUCENT RED invalid track with NO train, is NOT registered with the manager (guests never queue for it), console.errors the fix (end the layout FACING the station; keep every piece inside ±size/2) and fails validatePark hard. **POINTS mode runs the SAME fatal gate (round-2 safeguard)** — `checkCoasterDesign` (hard violations) + `validateSpline` (≥ 0.9 clearance) + park bounds (±size/2 + 0.4) over the as-built world points; `points` used to bypass every guard and run a 1.9 g out-of-bounds circuit as a live ride. `<TrackRide>` applies the same guard (bounds checked through its mount transform; previews are exempt). Required props (`queueTailNode`/`queueDir`, `deck` shape) are validated up front with named errors; **`exit`/`exitDir` are OPTIONAL since the 2026-07 RCT2 entrance/exit fix** — omit them and the exit hut takes the RCT2 cell one tile along the station face from the entrance, facing the same way out, on whichever side its exit path reaches the street soonest (see THE RCT2 ENTRANCE/EXIT LAYOUT below; every §4.0 archetype now omits them, and its old pinned `[start.x + 2.4, start.z + 2.4]` is republished as `[start.x + 1.69, start.z ± 1.2]`). **Queue-orientation safeguard (round-4):** the lane hangs off the FIXED tail node, so a `queueDir` aimed along the station row spears the ride's own pad/deck — the wrapper now auto-FLIPS to the first orientation of dir/-dir/perpendiculars whose lane + entrance hut clear the ride's own boardPoint pad/station straight/deck and stay in bounds (preferring one that also clears the planned exit), relocates the exit hut when the re-oriented lane runs over its cell, and `console.warn`s every choice (warnings are FATAL per the recipe book — fix the plan). `registerComposedRide`/`<ConfigurableRide>` apply the same safeguard to derived/provided lanes (explicit `queue.anchor` opts out). The circuit registers for validatePark WITH the ride name so the round-4 track-corridor sweep can exempt the ride's own access rects. Pieces-mode `start` accepts `[x, z]` OR the same `[x, y, z]` tuple given to `compileTrackPieces` (round-3 safeguard: a V3 start used to be read as `[x, z=y]`, shifting the whole circuit out of bounds), and `bank` SATURATES at the type's bankLimit (`coasterBankCap` — wooden 25°, steel 55°; the registered bank matches what is built, so validatePark's re-check agrees).
- **`<FlatRide build position name capacity rideDuration price intensity colours queueTailNode queueDir exit? exitDir?>`** — generic flat ride: your deterministic `build(t, { position, padTop, groundAt, scheme })` → `{ group, update?, seatWorld?, boardPoint? }` makes the visual (place it at `info.position`/`padTop` yourself); the wrapper wires the queue/hut assembly + registration. `exit`/`exitDir` are OPTIONAL: omitted, the exit hut is auto-derived the way every other wrapper derives it — the RCT2 cell ONE TILE along the station face from the ENTRANCE hut, doorway facing the same way OUT (`exitDir` defaults to `queueDir`), on whichever side its exit path reaches the street soonest. It used to take the local `[-1.5, 1.35]` cell with its doorway facing the queue frame's −x — the OPPOSITE face, with nothing leading away from it. All required props are validated up front with named errors (`"<FlatRide> 'X': exit must be [x, z] …"`) — a missing prop used to crash the whole page with a raw `undefined[0]` TypeError before anything mounted. STRANDED-AT-ORIGIN GUARD: a builder that ignores `info.position` (group AND geometry both > 0.5 u off the cell) has its group moved onto the cell with a warn, and a post-mount audit warns loudly whenever the mounted visual still sits > 0.5 u from `position` — sim pads must never register at an empty cell.
## `<ThemeRegion>` — designate part of the plot as one world (2026-07)

The **spatial half** of the theme abstraction. A `WorldTheme` (SetPieceKit's `WORLD_THEMES`) already described what a world *looks* like — paving, planting, lamp character, path surface, and now `furniture`. What was missing was a way to say *where* it applies, so every call site restated it: a `<Paths surfaceZones>` entry here, a `theme` prop on each set-piece there, and **nothing at all** for the benches, bins and lamp posts the park plants down its own streets. A caldera and a nightclub were furnished from the same municipal catalogue.

```tsx
<Terrain … />
<ThemeRegion theme="fire" position={[-7.2, 0]} extent={[3.0, 8.4]} />
<ThemeRegion theme="neon" position={[ 7.2, 0]} extent={[3.0, 8.4]} />
<Paths nodes={NODES} edges={EDGES} />   {/* ← both worlds' streets, automatically */}
```

Mount them **after `<Terrain>` and before `<Paths>`** (the network reads the registered regions when it builds). Then:

- **Roads pave themselves.** `<Paths>` DERIVES its `surfaceZones` from the registered regions, so nobody hand-lists a zone per world. An explicit `surfaceZones` still wins for full control.
- **The furniture on those roads follows.** `PathNetwork`'s `themeAt` resolves the theme at each verge point and buckets the merged meshes **by theme id** — a merged mesh carries one material, so themed furniture cannot share a bucket. With no regions there is exactly one bucket holding `DEFAULT_FURNITURE`, byte-identical to the `IRON_C`/`SLAT_C` pair the network used to bake in.
- **Anything else can ask.** `usePark().themeAt(x, z)` → `WorldTheme`, `themeFurnitureAt(x, z)` → `{ id, furniture } | null`, `themeRegions()` → the list. A component can dress itself from where it stands instead of being told.

`theme` takes a genre id — **`fire` · `steampunk` · `pirateBeach` · `enchantedForest` · `neon`** (or `default`), or a `WorldTheme` object of your own. They were place names until 2026-07; SetPieceKit/Context.md explains why genres, and the five legacy ids still resolve.

`position` is the centre and `extent` is **half**-extents; `rotation` takes a quarter turn. Two regions sharing an `id` share a furniture merge bucket, which is what you want for a world split across two rectangles. First match wins, so overlapping regions resolve in declaration order; outside every region you get `DEFAULT_THEME`.

**You still choose which pieces belong in a world** — a theme cannot know a caldera wants basalt rocks. What this removes is having to restate the world's *look* at every call site.

Worked example: `harness/park-eval/samples/theme-regions.tsx` (three worlds, one continuous lattice, `validatePark → ok`, and not one `surface`/`surfaceZones`/colour prop in the file).

## Lights are no longer throttled (reverted 2026-07)

The ride runtime used to shed a FAR/OFFSCREEN entry's PointLights outright and enforce a park-wide nearest-N **global light budget** (`budgets.lights`, defaulting to 16) on top. Both are gone by default. Measured on `monorail-ref` at size 128 by `harness/park-eval/probe-night-lights.mjs`, which counts lights that are LIT for the night but switched off by the runtime:

| | lights | night frame |
|---|---|---|
| cap 16 (old) | 41 total / **18 visible** / 24 lit → **11 lit-but-hidden** | 1148 draws · 0.54M tris |
| no cap (now) | 41 total / **41 visible** / 24 lit → **0** | 1148 draws · 0.54M tris |

The cap was switching off eleven of the park's twenty-four night lights — night mode's whole point — and the draw calls and triangles are **identical** either way, because a PointLight costs per-fragment shader work in forward rendering rather than draws, and at 24 lights that did not surface above the noise. Do NOT grade this by fps: under SwiftShader the same build measured 31.6 and 28.8 fps in the probe while the in-page perf line reported 7.6 and 11.9 for those same two runs.

Where the load time actually goes is **initial load, and it is terrain**: `probe-mount-cost.mjs` on the same park reports 1012 ms of build work, **452 ms of it `<Terrain>` and 378 ms of that inside `parkComposition`**, against a steady frame carrying 4 active lights. `budgets.lights` remains available for a scene you have measured; the per-component guidance is unchanged (the Stage still warns past ~8 real Point/Spot lights — prefer `nightKOf`-gated emissive materials, which is how most night lighting in this system is done and costs nothing).

- **`<Placed build position rotation scale>`** — the escape hatch: mounts ANY `(t, park) => Group | { group, update? }` at a settled position. It goes through the same ride runtime as every wrapper (LOD throttling, light budget), but prefer the composable catalog components / `composableRide` for rides — they add queue/hut/sim wiring on top of the same policy. Use `<Placed>` for Kit/Rock pieces and one-off dressing. Round-6: like `<Scenery>` it registers its GROUND-CONTACT footprint (the XZ extent within 0.45 u of its base — a tree canopy may overhang a path, its trunk may not), so `validatePark` fails a willow planted inside the waterline or a prop blocking the walked surface. AUDITS: a built group that already carries its own position (> 0.5 u off the local origin) warns — `<Placed position>` is added ON TOP; and a `build` function whose NAME matches `/Scene$/` (a `build<Name>Scene` preview stage builder) warns inside a real park — preview scenes are staging, use the component or its `build<Name>()` builder (best-effort name check, also applied by `useComposable`; wrapped/anonymous builders pass through undetected).
- Amenities: **`<Stall kind="balloon" position rotation sell?>`** (plinthed; routed through `<ConfigurableStall>` — round-3 safeguard: it now REGISTERS with the manager and carries catalog-stall userData tagging instead of being invisible to both; `sell` is `true` for the kind's sale defaults — balloon: item 'balloon', price 2, value 3 — or an override object), **`<Restroom position rotation>`** (registered — guests use it; the hut is a BLOCKER with its doorway left clear), **`<Fountain position? scale?>`** (defaults to the first plaza's centre; the basin is a circular BLOCKER — guests walk round it), **`<Torch position height?>`**, **`<Neon text|path color secondary scale backboard? position rotation posts?>`** (night-gated marquee on iron posts; default scale is AUTO — capped so the sign never exceeds ~2.5 u of width; explicit `scale` honoured; `backboard` defaults **OFF inside a park** — round-2 safeguard, a marquee backboard read as a monolithic black wall in ground shots — pass `backboard` to opt back in, and buildNeonSign then hugs the text and area-caps the slab), **`<DanceFloorR position size tile rotation>`**, **`<Scenery name position scale seed rotation>`** (SceneryPack catalog; round-6: registers its GROUND-CONTACT footprint so `validatePark` fails a piece planted in the water or standing in a path slab — plaza dressing exempt), **`<Lights from to poleHeight bulbs colors sag>`** (two real light poles + the catenary span hook-to-hook). Fencing lives in its own component — `import { Fence } from '../Fence'`: **`<Fence from to style height/>`** or **`<Fence points closed/>`** for a polygon (wood post-and-rail / metal queue railing / clipped hedge; from/to are WORLD xz so it takes no `position`, and every run registers as a guest BLOCKER — leave a GATEWAY where a street crosses it).
- `position` props take `[x, z]` (y settles onto the plaza/terrain under it) or `[x, y, z]`; `rotation` is Y yaw in radians.

## Round-5 self-healing settle pass (runtime-derived state)

Once ALL children have mounted — before guests spawn and before `validatePark` reads anything — `<Park>` runs two self-healing passes over the RUNTIME-DERIVED state no static plan can reliably predict (derived/trimmed/flipped/audit-shifted rigs, compiled circuits):

1. **Corridor auto-resolution.** Every MOVABLE object (stalls via `<ConfigurableStall>`/`composableStall`, flat-ride rigs via `registerComposedRide`/`<FlatRide>`; tracked-circuit rides and streets never move) is swept against the registered coasters' 1.6-u track corridors (the same segment-OBB sweep `validatePark` runs). Collisions self-heal in quality tiers: an exit hut alone in a corridor relocates by itself (0.6-u steps, ≤ 3 u); otherwise the whole rig shifts outward along the least-move axis to the first clear cell (≤ 4 cells; axis before diagonal, no-overlap before keeps-pre-existing-overlaps, corridor-fully-clear before exit-follow-up, dry before wet, never onto a hill flank or out of bounds); a derived queue lane too long to fit anywhere trims (`mgr.resizeRideLane`, fewer slots) as the last resort. Every fix is recorded as a **§0-FATAL park lint** (round-6: `console.warn` + `report.warnings`, and `validatePark` fails it as check `autofix`) — a self-heal is a REPORT, not a pass; the `pinned` prop opts a ride/stall out (it then FAILs where it stands). `manager().corridorCells(name?)` exposes the corridor cells for planning.
2. **AUTO-keepDry (`reclampTerrain`).** All audited footprints (manager + `registerFootprint` extras + stall rects) plus the as-built circuits feed the ParkBuilder guard clamp; when anything was wet/bulged/burying, `<Terrain>` rebuilds the terrain mesh, climate/zone colours, `heightAt` sampler and lint IN PLACE (the auto-dressing re-settles onto the new ground). Authors' `<Terrain keepDry>` is a hint, not a requirement — but every self-heal is a warning: a layout that needed one was mis-planned.

## Round-6 safeguards — auto-fixes reach the GATE (§0's fatal-warnings policy)

`rules/park-generation.md` §0 calls every grid/closure/`placeAccess` warning FATAL, but before round 6 the wrappers' auto-fixes were console-only: a park shipped `ok: true` over a flipped `queueDir`, a 2.21-u causeway and a relocated exit hut. Now:

- **`park.reportLint(kind, detail, fatal?)`** (on the ParkContext) records a build-time lint/auto-fix event. `<Park>` hands the list to `validatePark`, which echoes ALL of them in the new **`report.warnings: { kind, detail, fatal }[]`** and promotes `fatal: true` ones into real `failures` with check **`'autofix'`** — plus every kind in validate.ts's `FATAL_LINT_KINDS`, so the gate owns the §0 policy even for lints recorded by a wrapper that cannot know it. FATAL today: `causeway`, `queueDirFlip` / `queueDirUnfixable`, `exitHutRelocated` / `exitHutUnfixable`, `corridorShift` / `corridorExitRelocated` / `corridorLaneTrim` / `corridorPinned` / `corridorUnresolved`, and (round-6) **`coaster:shortDrop`** — a first drop under RCT2's 0.9-u gate HALVES excitement/intensity/nausea (`RideRatings.cpp:1318`), so the coaster opens as a ride nobody rates; every §4 archetype publishes lift ≥ 1.0 precisely so this can be a hard failure. Reported but NOT fatal: `laneTrim` (the round-2 tail-on-node trim working as designed — it still starves queue slots, so it is worth reading), `exitNotAdjacent` / `exitFaceBlocked` / `exitLaneUnreachable` (the RCT2 entrance/exit layout — see below; adjacency is convention, not a rule RCT2 enforces), `coaster:shortLength` (a short circuit is a deliberate kiddie-coaster choice). **An empty `warnings` array is the only truly clean result.**
- **`park.registerPlanted({ label, x, z, r })`** — `<Scenery>`/`<Placed>` register their ground-contact footprint, and `validatePark` gains a **`scenery`** check: nothing planted may stand in the water (`terrainLint.isDry`) or inside a rendered path slab (plaza dressing exempt; the blocking radius caps at 0.6 u so a walk-in gazebo abutting a path stays legal).
- **Hard `bounds` check** — every audited footprint's SWEPT corners and every GameManager-derived queue-tail/exit attach node must sit inside ±size/2. `resolveQueueOrientation` now also tests the LANE rect and its derived TAIL for bounds (it used to test only the hut), so an orientation that would put a queue tail off the plot is flipped away from instead of shipped.
- **Strict track-corridor re-audit** — beside the 1.6-u corridor / 2.2-u ground clearance, every audited rect is re-swept at 2.2 u wide against the obstacle's OWN ROOF (hut 1.5 u, stall canopy 2.1, lane 0.45, pad 0.6, +0.3 u clearance). A hut the runtime relocated 0.96 u from the rails with the track 0.59 u off the ground used to pass; a roof-skim now FAILs.
- **`<Coaster>` crash gate in BOTH modes** — the energy-paced `replayCoasterForces` profile (the same physics `validatePark` and `rateCoaster` use) runs on the as-built world points for `points` AND `pieces` mode. Over the 1.5 g no-upstop derail guard (×0.85 margin) the circuit is FATAL: translucent red track, no GameManager registration. A 1.46 g circuit used to print "points-mode checks → design ok: true" and carry guests.
- ~~**Derived exits snap to the paving**~~ — **REPLACED 2026-07 by the RCT2 entrance/exit layout (below).** The round-6 snap re-picked among the ride's four flush pad-edge cells "never the queue's own side", i.e. it deliberately put the exit on a DIFFERENT face from the entrance, and paired that with `exitDir = −queueDir`. It shortened the walk to the paving but kept the wrong shape, and nothing led away from the hut at all.

## THE RCT2 ENTRANCE/EXIT LAYOUT (2026-07) — a ride has TWO paths

**Measured before the fix, over the seven reference parks: 26 rides, ZERO entrance/exit pairs in the RCT2 arrangement, 25 exits standing on bare grass** (up to 14.4 u from the nearest paving), several at diagonal yaws RCT2 cannot represent. Guests unloaded onto a meadow. After: **26/26 adjacent-and-outward, 0 stranded**, every exit with its own paved run to the street.

**What RCT2 does** (verified in `src/openrct2/`, and it corrects the usual assumption):
- the entrance and exit each stand on a full tile ADJACENT TO THE STATION on a side the track sequence permits — ENFORCED by the placement tool (`openrct2-ui/ride/Construction.cpp:449-487`) and re-enforced by `Ride::validateStations`, which DELETES one that stops qualifying (`RideConstruction.cpp:1557-1592`, the relative-direction test at **:1584**);
- the stored `direction` points **INWARD**, at the station, and BOTH paths attach on the reverse side (`kEntranceDirections` = 4, `EntranceElement.cpp:22-26` + `Footpath.cpp:118-121`). Our `queueDir`/`exitDir` are that reverse — the outward facing, the sense of `gRideEntranceExitPlaceDirection` (`Construction.cpp:479-483`) — and always one of four cardinals;
- the entrance takes a **QUEUE** (`FootpathChainRideQueue`, `Footpath.cpp:794-921`) and the exit takes an **ORDINARY FOOTPATH**: a guest finishing a ride is put down on the tile immediately OUTSIDE the exit (`Guest.cpp:4412-4452` → `:5092-5140`) and, with no path there, `Peep::UpdateFalling` drops them onto bare terrain (`Peep.cpp:781-890`) or drowns them over water (`:831-854`), while the park carries a recurring red `STR_EXIT_NOT_CONNECTED` — *"has no path leading from its exit! Construct a path from the ride exit"* — for as long as the ride is open (`Ride.cpp:2076`);
- **adjacency is NOT enforced.** `RideStation` holds two independent `TileCoordsXYZD` (`Ride.h:172-173`) and no code compares them; each is validated only against the station track. Entrance-beside-exit is player convention — the thing every RCT2 park is actually built from.

**What the chassis now builds.** `registerComposedRide` / `<FlatRide>` / `<Coaster>` all derive:

```
entrance hut = queueAnchor − queueDir·0.62
exit hut     = entrance hut ± 1.2·[−queueDir.z, queueDir.x]      // ONE TILE along the face
exitDir      = queueDir                                          // both doorways face OUT
```

Both huts sit at the same depth off the face, so the exit clears the ride body by exactly the 1.27 u the entrance hut does — the old flush-to-the-−x-pad-edge clamp is gone with the absolute cell it clamped. Between the two candidate sides the chassis picks the one whose **EXIT PATH is shortest** (`pickAdjacentExitCell`, ray-cast against the real lattice), skipping cells that are out of bounds, wet, or on an audited footprint. Where BOTH are illegal it keeps the hinted one, faces it outward, and records an `exitFaceBlocked` lint — it does NOT repair onto another face, because that repair is what produced the stranded exits.

**The EXIT PATH itself** (`GameManager/access.ts` `planExitLane` / `buildExitLane`) is an ordinary grey **unfenced** `SURFACE_TARMAC` slab — never the red queue — cast from `exit + 0.62·exitDir`, cardinal only, in at most two legs: **THE RAY** (straight along `exitDir` to the first street node/edge inside 9 u — with the adjacent layout this is the cross-street through the queue's own tail node, at the same `laneLenOf(capacity) + 0.35` the queue takes) or, when the tail is a dead-end court spur with no cross-street, **THE JOIN** (out level with the tail, then one tile onto it — what a player actually builds). Shorter wins. Both legs are registered footprints (`<name> exit lane`, `<name> exit lane join`) so the OBB sweep, the `bounds` check, the wet-pad guard, AUTO-keepDry and the track-corridor sweep all audit them exactly as they audit the queue lane. `moveRide`/`moveRideExit`/`resizeRideLane` re-cast the run in place (`replanExitLane`) — unlike the queue lane it is pinned at BOTH ends, so it cannot simply travel with a shifted rig.

**Guests use it.** `rideFsm.unloadRiders` already walked riders `exitDoor → exitAttach`; `exitAttach` is now the point where the exit path MEETS THE STREET instead of a bare 1.5 u step onto grass, so the whole walk out is on paving.

**Authoring.** `exit`/`exitDir` are OPTIONAL on `<Coaster>` as well as `<FlatRide>` — **omit them**; the chassis knows the RESOLVED queue direction (the orientation resolver may flip it) and ray-casts both sides. A hand-pinned pair is HONOURED and, when not adjacent-and-outward, reported as an `exitNotAdjacent` lint naming the cell that would have worked. `RideLayout.exit` on a catalog component is now only a SIDE HINT — the chassis reads the sign of its local x and nothing else.

**Gate (`validatePark` check a4; rules/park-generation.md §0.4b).** A missing or unroutable exit path is a hard **`accessibility` FAIL**, symmetric with "gate cannot route to the `<ride>` queue tail" — RCT2 blocks `Ride::open` outright on a missing exit (`Ride.cpp:2366-2412`) and permanently flags an unpathed one, and here it is strictly worse than in RCT2 because this sim has no terrain-walking `falling` state: the guest is simply left off-graph. Entrance and exit NOT on the same outward face is an **`exitNotAdjacent` warning**, because RCT2 provably permits it (see above) and failing it would condemn legal long-station layouts — §0's fatal-warnings policy still means a park carrying one needs re-planning.
- **SOLIDITY (`park.registerBlocker`) — guests no longer walk through things.** Guests used to clip straight through fountain basins, ride bodies and fences. Now every solid object registers a world-space OBB/circle with the GameManager's **blocker registry** (GameManager/Context.md "Blockers"): the routing layer refuses path edges that cross one, off-network waypoint hops SLIDE along the edge instead of entering, and `validatePark` gains a **`blockers`** check — no rendered street edge may run through a blocker (sampled every ~0.3 u; access spurs exempt) and every ride's queue tail must stay reachable from the gate with the blockers respected. Registered automatically: each ride's boarding pad + BODY footprint (`registerComposedRide`/`<FlatRide>` measure the built visual), each stall's body (the serving front stays walkable), `<Fountain>` (a circle at the basin radius), `<Restroom>` (hut solid, doorway clear), both queue-lane railings, and every `<Fence>` run. Relocations (`moveRide`/`moveStall`/`resizeRideLane`, the corridor auto-resolver) move the blockers with the rig. **Fence a boundary with a GATEWAY where a street crosses it** (two runs with a gap, or `<Fence inset>`) — a fence laid across a street is a hard FAIL, not a lint.

## Round-7 safeguards — the STREET/PLACEMENT layer (rules §0.14-§0.18)

Round 7's park scored its coaster 8/8 and still failed `validatePark` with 34 failures — EVERY one of them in the placement layer. These close those defect classes at MOUNT time, with an actionable message and a suggested cell, instead of as downstream FAILs:

- **Pads off the lattice.** `registerComposedRide` and `<ConfigurableStall>` audit the mounted pad against the RENDERED street lattice (`lintPadOffLattice`). A pad INTERSECTING a slab is a §0-FATAL **`padOnStreet`** lint; a ride pad inside the 1.8-u §0.14 margin but clear of the slab is a **`padNearStreet`** warning. Both print the nearest legal cell, computed with the same **`offPathCell(net, [x, z], { clear })`** / **`pathClearance(net, [x, z])`** helpers authors can call (exported from `../Park`). A SHOP is audited on its SOLID BODY only (hx 0.6 × hz 0.42) — kiosks are SUPPOSED to abut the street, so a `<Bazaar>`'s stalls may flank its own aisle.
- **`queue.anchor` is the HEAD — and a tail passed as one is AUTO-CORRECTED (wave-9).** An explicit anchor landing ON a street node is moved to `node − dir·(laneLenOf(capacity) + 0.35)` and reported as a **`queueAnchorIsHead`** WARNING naming the value used. It used to be a §0-FATAL lint that printed the right number and then kept the broken lane: round 8 shipped two such lanes running down the street and paid 5 `footprints` + 3 `padOnStreet` + 8 `blockers` FAILs and a dead sim (`queued 0 / riding 0`) for them. Write the corrected value into the park — and note that the fix moves the LANE, not your PAD (§0.14 still applies). Round 7 got this wrong on five rides and never saw it, because `composableRide` was dropping `queue` (and `name`/`capacity`/`intensity`/…) into the visual builder's props instead of forwarding them to the chassis. **They are forwarded now.**
- **Two rides, one tail node** → §0-FATAL **`queueTailShared`** (one cell cannot be the entrance to two queues).
- **`<Paths>` derives ONE level from the MEDIAN ground** under its nodes (not the max) whenever the node spread exceeds 0.35, auto-ramping the outliers (`pathLevelMedian`, non-fatal) instead of hoisting the whole street onto berms. A span over **2.0 u** of air, or one whose ground dips under the waterline, is **NOT BUILT** — the edge is dropped and a §0-FATAL `causewayRefused` / `latticeInWater` lint says so, which then manufactures the DOWNSTREAM `accessibility` failures for whatever sat behind the hole.
- **Composed-terrain query API** (`park.terrain`, `park.isDry(cell)`, `park.isDryCell(cell)`): the §1 seed table's water coordinates are PRE-GUARD and move when `keepDry` forces a re-pick, so authors can finally read where the lake LANDED. `<Scenery>`/`<Placed>` refuse to plant in OPEN water (§0-FATAL `plantedInWater`); a marginal shoreline cell is kept and the AUTO-keepDry pass raises a dry bank under it (`plantedWetCell`) — planted footprints now join that sweep.
- **Stalls take the object form** `register={{ name, price, value, item }}` (it used to be a rides-only spelling that stalls silently ignored, so parks shipped catalog default names). The sibling spelling works too and WINS: `<SodaStand register name="Lakeside Soda" price={2} value={4} />`. `ConfigurableStall` resolves `name ?? register.name ?? catalogDefault` — VERIFIED in source, and both forms reach the GameManager. (A wave-9 audit found the *harness eval tag* reading only the sibling `name`, which is why a probe once reported a correctly-themed stall as `defaultNamed: ["Soda Stand"]`. The design system was right; the probe was fixed.) Duplicate stall names and duplicate/unnamed registered CIRCUITS warn: the manager and the corridor sweep both key on the name.

Rules and limitations:

- **Deterministic only** — wrappers use hashed-sine randomness seeded off `<Park seed>`; never `Math.random`.
- **Prop changes REMOUNT the object** (rebuild + dispose). GameManager registrations (rides, stalls, restrooms, the gate) can NOT be unregistered — to change sim config, remount the whole `<Park>` with a `key`. Builder-function props (`build`) are not remount keys; keep them stable.
- **Every catalog ride is directly composable and registers itself** — `<FerrisWheel position register/>`, `<Carousel>`, `<Teacups>`, `<DropTower>`, `<GhostTrain>`, the food shops, and the rest. Pass `register` (or `register={{ name: '…' }}`) and the ride appears in the GameManager with a queue, entrance, exit and exit lane derived for you. You do NOT need `<Placed>`+`usePark().manager()` for a catalog ride; reach for `<Placed>` only for scenery and for rigs with no wrapper of their own. `<Coaster>`/`<TrackRide>`/`<FlatRide>` are the chassis the wrappers are built on, not a substitute for them.
- **The worked example is `DistrictPark`** (`Park.previews.tsx`, preview 1): a size-48 park whose streets are FUSED by `buildParkNet` from a `<FountainPlaza>` + `<Bazaar>` + `<Boulevard>` plus a 13-node spine, with a pieces-mode §4.0-A flagship, three flats on cell interiors, and the composed water read from a guarded probe — `validatePark ok: true`, 0 failures. `DemoPark` remains as the COMPACT size-16 variant, but it is NOT the layout to copy (hand-written lattice, points-mode coaster): pointing agents at it is what produced four hand-rolled-grid parks in rounds 6-7.

FILE LAYOUT (implementation detail — ALWAYS import from `../Park`, never a sibling directly): `parkContext.ts` (the park store/context, `usePark`, LOD + light budget runtime) · `parkRoot.tsx` (`<Park>` provider + Stage host) · `composable.tsx` (`useComposable`, `composable()`, `<ScenePreview>`) · `configurableRide.tsx` (`<ConfigurableRide>`, `<ConfigurableStall>`, `composableRide`/`composableStall`, `registerComposedRide`) · `wrappersLand.tsx` (the two SYNCHRONOUS land wrappers — `<Terrain>`/`<Paths>`) · `wrappers.tsx` (the QUEUED content wrappers — `<Gate>`/`<Coaster>`/`<FlatRide>`/`<Placed>`/`<Stall>`/`<Restroom>`/`<Fountain>`/`<Torch>`/`<Neon>`/`<DanceFloorR>`/`<Scenery>`/`<Lights>`/`<GameManager>`/`<ElevatedWalkway>` — and it re-exports `<Terrain>`/`<Paths>` by name, so `./wrappers` is still the one import surface) · `pieces.tsx` (JSX track pieces + `compileTrackPieces`) · `index.tsx` (the public re-export surface).

`wrappers.tsx` was 82 KB and `ParkBuilder/composition.ts` 109 KB — both past what a single design-system write call can emit — so 2026-07-26 split them behind the existing module layout: `Park/wrappersLand.tsx` took `<Terrain>`/`<Paths>`, and `ParkBuilder/` gained `landform.ts` (composition types + terrain/water primitives), `ranges.ts` (`makeRangeComposer`), `sections.ts` (`computeReliefFloor` + `composeLandZones`) and `reclamp.ts` (`reclampTerrain`), with `parkComposition`, its memo cache and `composeParkUncached` kept together in `composition.ts`. Every public export name is unchanged and re-exported BY NAME; no behaviour moved with the code. Note for the harness: `park-eval/evaltags.mjs` anchors source TEXT, so its `<Terrain>` injection is keyed on `wrappersLand.tsx` now and the esbuild `filter` admits that path — re-check `auditAnchors()` after any further reshuffle.

## Initial load — what it actually costs, and what streams

Measured with `harness/mp3d-render/probe-mount-cost.mjs` (long tasks + the worst gap between animation frames, which is what a user experiences as "the page froze"), on the 6-ride `coolpark-a` sample:

| | cost |
| --- | --- |
| `parkComposition` (the deterministic park plan) | **601 ms** |
| `buildTerrain` heightfield + mesh | 185 ms |
| buildWater / dressTerrain / buildSurround | 39 / 33 / 3 ms |
| **all 20 component builds put together** | **54 ms** |

The intuition that "the rides are heavy" is wrong by an order of magnitude — the whole content of a park is 54 ms and the LAND is 861 ms, 70% of it in the composition search. Two changes follow from that.

**1. Everything that mounts on the land now STREAMS.** `useComposable` and the ten content wrappers (`Gate`, `FlatRide`, `Placed`, `Restroom`, `Fountain`, `Torch`, `Neon`, `DanceFloorR`, `Scenery`, `Lights`) queue their build through the store's `enqueueBuild` instead of running it inline, and the queue drains with an 8 ms budget per tick. The queue is strictly **FIFO**, so every build still happens in the React effect order it always did — `floorAt` still sees the terrain, registrations still land after the manager, `<Paths>`'s re-settle still follows `<Terrain>`'s reclamp. Only the timing changes. `<Terrain>` and `<Paths>` are deliberately **NOT** queued: every other wrapper guards on them (`needs <Terrain> and <Paths> mounted first`) at effect time, and they are also what should appear first anyway.

**Yield with a macrotask, never `requestAnimationFrame`.** The first version drained one chunk per animation frame, which ties build progress to the frame rate — and on a weak GPU a frame is not 16 ms. Measured under SwiftShader at 446 ms/frame, a 19-build park spent ~8.5 s purely waiting for paints: chunking had made time-to-ready far WORSE than building synchronously. A `setTimeout(0)` yield keeps total build time essentially the same as synchronous while still letting the browser paint and take input between chunks.

**Do not trust the harness's "worst frame gap" as the score.** Under SwiftShader a frame costs ~450 ms and `validatePark`'s 60-second sim smoke is one synchronous block, so that metric is dominated by software rasterisation and the smoke, not by the build — across runs it read 11.2 s, 5.8 s and 13.1 s for the same code. The hardware-independent numbers are the per-build marks in the table above; the user-facing gain needs measuring on a real GPU.

Anything that needs a COMPLETE park must use **`whenBuilt(cb)`**, not one `requestAnimationFrame` — `<Park>`'s settle/validate pass does, or `validatePark` would audit a park that is still assembling and fail everything. `flushBuilds()` runs the queue synchronously for probes and tests, and the `sync` argument `whenBuilt` hands its callback says which of the two drained the queue.

**3. THE PARK DOES NOT RENDER WHILE IT ASSEMBLES (2026-07-28).** Streamed content mounts INVISIBLE (`addObject` hides anything added while the queue is draining) and `revealBuilt()` shows it in one step, after the settle pass has moved everything to its final place. `<Terrain>` and `<Paths>` are synchronous, so the land and the street are on screen from the first frame and the user watches a real park appear rather than a blank sky.

The reason is shader programs, not aesthetics: three.js keys a material's program on the number of VISIBLE lights, so a park that renders a hundred intermediate states compiles the same shaders at a dozen different light counts, and every one of those compiles is a synchronous stall. Measured on `parkA-99` (size 128), M4 Pro at `--throttle=4`, `harness/mp3d-render/probe-assembly.mjs`:

| | render while building | hidden until revealed |
|---|---|---|
| long tasks | 113–116 (16.0–16.2 s) | 19 (9.6 s) |
| worst freeze | 3.36 s | 2.94 s |
| median frame during load | 59–64 ms | 28 ms |

Two rules if you touch this. `revealBuilt()` is ONE-WAY (`_revealed`) — a component that rebuilds after the park opens has no second reveal, so nothing may mount hidden after it. And only objects that were VISIBLE when they arrived are recorded, so a component that mounts its own group hidden is never force-shown — the same "only restore what I shed" rule `Stage/darkLights.ts` follows for lights.

**4. THE ACCEPTANCE GATE RUNS AFTER A PAINT.** `validatePark` costs 1.8 s on parkA-99 at `--throttle=4` and used to run in the same task as the drain, so the moment the park became ready to look at, the main thread locked for the length of the gate. It is deferred by one frame now (a flushed queue still gets its report synchronously — a probe that asked for a complete park in this task is entitled to one). `ParkStore._settling` holds the sim clock frozen across the gap, for exactly the reason regression 2 below describes: the smoke run steps `manager.update` from ~0 and real frames must not have carried the manager forward first.

**2. `parkComposition` is memoised.** It is a pure deterministic function of (seed, size, climate, guards) — the property the whole seed table rests on — and it cannot be made cheaper without changing what it returns, which every park's layout and every recorded seed-table number depends on. So the first call still pays 601 ms; what it no longer does is pay it AGAIN for the same question, which it was doing on every `<Terrain>` prop change, every StrictMode double-invoke and every editor remount. Cache hits hand out a **deep clone** of an untouched snapshot, because the composition is mutated after creation (`reclampTerrain` pushes guard discs into `clampPeaks`/`clampBasins`) and sharing one instance would leak the previous mount's discs into the next park. Cloning is not free — ~119 ms against a ~480 ms compose, so a hit is about 4× faster rather than instant. `harness/mp3d-render/probe-composition-cache.mjs` gates determinism, isolation (mutate one result, prove the next call is unaffected), key discrimination and that speedup.

**Two regressions this introduced, both caught by the existing gates — worth knowing before touching the mount path again:**

1. **Queueing only SOME components silently inverts order.** Anything not queued runs during the commit while queued builds drain after it, so a synchronous `<Coaster>` registered before a queued `<Gate>` had planted the park entrance. `validatePark` failed with `[sim] no guest completed a ride cycle in 60 sim-s` on a park whose build logs were otherwise byte-identical. Every content component must go through the ONE queue.
2. **Frames now render DURING the build, which rewound the sim clock.** The smoke steps `manager.update(s · dt)` from ~0; once real frames had carried the manager to t ≈ 8 s, the smoke sent time backwards and every FSM timer landed in the future — the same flat `[sim]` failure. `<Park>`'s frame loop now HOLDS the sim clock while `_buildQ` is non-empty, which is also the right behaviour on its own terms: guests should not walk into a park that is still missing half its rides.

And one harness trap: reindenting a wrapper body broke an `evaltags.mjs` source anchor (`built.group.userData.rideRef = handle;` pinned at its exact 4-space indent), which degrades a probe axis silently rather than failing. That anchor is now a RegExp and `auditAnchors()` handles both kinds — run it after any edit to a wrapper. **The count is 18 anchors, 0 broken** (this line said 17 until 2026-07-26; the 18th is `parkRoot.tsx`'s `__parkReport`/`__parkSettled` publish, added in this same wave and never counted here). Splitting `wrappers.tsx` moved the `<Terrain>` anchor to `wrappersLand.tsx`, which is a KEY change in `INJECTIONS` *and* a change to the esbuild `filter` — `wrappers` alone cannot match `wrappersLand.tsx`, so omitting it would have dropped the terrain/water axis silently. Audit the COUNT as well as the broken list: an anchor that stops being reported at all is the same silent degradation as one that stops matching.
